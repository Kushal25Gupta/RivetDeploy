1. Executive Brief
RivetDeploy is a self-hosted deployment orchestration platform inspired by the infrastructure patterns behind modern deployment platforms. A user connects a GitHub repository, triggers a deployment, and RivetDeploy schedules and executes the build in an isolated Docker environment, stores the immutable build artifacts in Google Cloud Storage, activates a deployment version, and serves the site through the routing layer.
The project is deliberately designed around engineering problems rather than feature count: asynchronous job orchestration, safe execution of untrusted build commands, immutable deployments, failure recovery, real-time visibility, and measurable performance.
The final project must demonstrate a complete working path, deliberate failure tests, and real benchmark data. Example metrics in this document are targets for measurement format only; never publish fabricated numbers.
2. Product Statement
From commit to controlled deployment.
RivetDeploy turns a Git commit into a controlled deployment artifact through a traceable state machine and an isolated build runtime. Every deployment has a unique immutable identity, a full event trail, and a recoverable lifecycle.

6. Cloud Architecture Decision
Important: do not design the production system around running a Docker daemon inside a normal Cloud Run service. Cloud Run provides managed container execution, including services, jobs and worker pools, but RivetDeploy needs direct control over ephemeral Docker build containers, resource limits and cleanup. Therefore the final design separates the control plane from the build plane.
Cloud Run: Spring Boot API/control plane.
Compute Engine: dedicated build worker host(s) running Docker and the RivetDeploy worker process.
Cloud SQL: durable PostgreSQL metadata.
Redis: shared queue implementation after the initial in-memory phase.
Cloud Storage: immutable deployment artifacts.
Artifact Registry: RivetDeploy API/worker images.
Secret Manager: GitHub and cloud secrets.
Load Balancer + Cloud CDN: production static delivery path.
Terraform: creates and updates cloud infrastructure.
This separation is a design feature, not a workaround: it makes the build executor an explicit platform component that can be benchmarked, isolated and scaled.

9. Deployment State Machine
QUEUED   |   v CLONING   |   v INSTALLING   |   v BUILDING   |   v UPLOADING   |   v DEPLOYED  Failure terminals: CLONE_FAILED INSTALL_FAILED BUILD_FAILED UPLOAD_FAILED TIMEOUT SYSTEM_FAILED CANCELLED 
All state transitions must be explicit and validated. A deployment must never jump directly from QUEUED to DEPLOYED, and terminal states must not transition back into active build states.
10. Required Deployment Lifecycle
1. Create deployment record with a unique deployment ID and commit SHA.
2. Persist state QUEUED.
3. Publish job to FIFO queue.
4. Worker claims job and moves state to CLONING.
5. Worker creates an ephemeral build workspace/container.
6. Clone the requested repository/commit using the approved GitHub integration.
7. Install dependencies inside the build environment.
8. Run the configured build command.
9. Capture stdout/stderr as deployment events.
10. Locate and validate the build output directory.
11. Upload output to a unique Cloud Storage deployment prefix.
12. Activate the deployment by updating the project active-deployment pointer.
13. Mark deployment DEPLOYED and emit final event.
14. Always perform cleanup, including on timeout/failure/cancellation.

18. Security Requirements
Never run arbitrary user builds in a privileged container.
Run build processes as non-root where practical.
Apply CPU, memory and execution-time limits.
Prevent leaked credentials from appearing in build logs.
Validate GitHub webhook signatures.
Validate and authorize every project/deployment access from the backend.
Use short-lived or scoped cloud credentials where practical.
Keep secrets in Secret Manager in production.
Never commit real credentials to Git.
Ensure containers and temporary workspaces are cleaned even after failures.
Validate repository URLs, commands and output paths to reduce path/injection risks.
Log security-relevant failures without logging secrets.

29. Data and Event Rules
Every deployment has one immutable deployment ID.
Every deployment records the triggering commit SHA.
Every state change produces a timestamped event.
Terminal deployments must contain enough failure information to explain why they ended.
Active deployment is a pointer/reference, not a mutable copy of artifacts.
Artifacts are never modified after a deployment is marked immutable.
Rollback only changes the active deployment reference.
User ownership is checked on every protected resource read/write.

32. What Not to Claim
Do not claim “production-grade” unless the implemented controls and deployment environment justify the phrase.
Do not claim “multi-tenant” unless resource ownership and authorization are implemented and tested.
Do not claim a benchmark number until the benchmark has actually been run.
Do not claim “secure sandbox” as an absolute guarantee; describe the controls actually implemented.
Do not call it a Vercel clone in the project title.
